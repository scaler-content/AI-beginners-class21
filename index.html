§ 1

Pick a Platform — Vercel vs. Render vs. Railway

⏱ 12 min

Three names get thrown around interchangeably as "free hosting." As of today, they are not the same offer — and picking the wrong one for the job costs either money or reliability.

🏠
The Analogy

Think of these as three kinds of premises for a shop. Vercel is a display window — brilliant for something that just sits there and shows itself, cheap to keep lit, but you can't run a kitchen behind it. Render is a small rented kitchen — it can actually cook (run a real backend), but if nobody's ordering for fifteen minutes straight, the stove goes cold and the next order takes a minute to get going again. Railway used to hand out a starter kitchen for free indefinitely; today it hands you a one-time voucher that runs out.

PlatformWhat it's actually free for (Sept 2026)The real gotcha
Vercel (Hobby)Forever-free for static sites and light serverless functions. 100GB bandwidth/month, 100K function invocations, 10-second max function duration, custom domains included.Personal, non-commercial use only — the Hobby plan's terms explicitly forbid client work and commercial SaaS. A bookshop's internal tool is fine; selling the tool to other bookshops isn't.
Render (Free web service)750 free instance-hours/month, real Docker-capable backends, free PostgreSQL (30-day expiry).Spins down after 15 minutes of inactivity. The next request wakes it back up — but that first visitor waits 30–60 seconds staring at a loading spinner.
RailwayA one-time $5 trial credit, no card required to start. That's it — there is no longer a standing free tier.A single small always-on service burns the entire $5 credit in about three weeks. After that it's a real bill, starting around $5/month minimum.
Curriculum honesty flag: Railway removed its permanent free tier back in 2024 — what remains is a one-time $5 trial credit that behaves nothing like an ongoing free plan. That's real, and the comparison table above says so plainly. It's still worth putting hands on today: a small, lightweight backend app comfortably fits inside that $5 credit for a single class session, which is enough to run a fair, live, side-by-side comparison against Render. What it is not is a plan for keeping something running for free indefinitely — say that part out loud, every time Railway comes up.

§ 2 · Build 1

shelf-talker.html → GitHub → Vercel, Live in Minutes

⏱ 24 min

No new code today. The exact same file from Class 17, pushed to a place Vercel can see it, and given a public address.

Why a single HTML file is the easiest possible deploy target

There's no build step, no dependencies to install, no server code to run — the whole "application" is one file a browser can already open. Deploying it is really just: put the file somewhere Vercel can fetch it, and let Vercel serve it to anyone who asks. That's the entire job. Nothing about deployment is conceptually different for a complex app — it just has more moving parts to wire up.

Before You Push — Confirm Git & GitHub Are Ready

Everything from here on assumes two things already exist on every laptop in the room: Git installed locally, and a free GitHub account. Neither has come up yet in this course — Class 17's shelf-talker file only ever needed VS Code, never a repository. Run this check once, right now, before touching the steps below — it covers both builds today, not just this one.

Check 1 · Git installed?Open a terminal and run git --version. A version number back means it's already there — skip straight to Step 1 below.
Missing, on MacRun git --version anyway first — macOS often offers to install Apple's Command Line Tools right there, which includes Git. If it doesn't prompt, install directly from git-scm.com/download/mac.
Missing, on WindowsDownload the installer from git-scm.com/download/win and accept the defaults on every screen — that's the standard setup, nothing to customize.
Check 2 · GitHub account?If you don't already have one, sign up free at github.com/join — just an email and a password, about two minutes, no card required.
Say this out loud before starting: if either check comes back missing, fix it now, before Step 1 — every remaining step in today's class, in both builds, assumes a working git command and a logged-in GitHub account. Five minutes spent here saves everyone getting stuck mid-push later.

  1. Turn the folder into a git repository. Open a terminal in the folder containing shelf-talker.html and run: 
    # Terminal — run inside the shelf-talker folder

  2. Create an empty repository on GitHub — github.com/new, name it shelf-talker, leave "Add a README" unchecked (Nikhil's folder already has the one file that matters), click Create repository.

  5. Import the repository: on the Vercel dashboard click Add New… → Project. Under "Import Git Repository," find shelf-talker in the list and click Import.

§ 3

Environment Variables & API Key Security

⏱ 16 min

The shelf-talker page had no secret to protect. The moment an app calls a paid LLM API, that stops being true — and this is where most real, avoidable damage in this whole course actually happens.

🔑
The Analogy

An API key is a shop's spare key, not its address. The address — the code, the logic, what the app does — is fine to hand anyone, and on GitHub it's usually meant to be public. The spare key opens the till. Writing it directly into a file that gets pushed to a public GitHub repo is the digital version of taping the shop key to the front window with the address.

Environment Variable

A piece of configuration — like an API key — stored outside the code itself, in the hosting platform's own settings, and handed to the running app only at runtime. The code refers to it by name (process.env.GEMINI_API_KEY, for example) and never contains the actual value. Push the code to a public repo all day — the key was never in it.

⚠ Documented, Not Hypothetical

This is a well-tracked category of real incident

GitHub's own secret-scanning system exists specifically because this keeps happening at scale: it checks every push, commit, file upload and API request against known secret patterns before the push even completes, covering roughly 70 different provider token formats. When a live key does slip through and land in a public repo, GitHub's partner program notifies the provider directly so the key can be revoked — often before anyone malicious finds it. None of that infrastructure would exist if hardcoded keys in public repos weren't a routine, recurring event.

The Near-Miss, Chapter One Shaped

What it would look like here

Imagine Nikhil pastes Restock Radar's Gemini API key straight into a config.js file "just to get it working today," pushes the repo to GitHub as public (so Ravi can glance at the code later), and moves on. Nothing bad has to happen immediately — but the key is now sitting in the commit history of a public repo, discoverable by anyone, including automated scanners that exist purely to find exactly this.

🎙 Instructor Says

"The fix is not 'be more careful.' The fix is a rule that removes the temptation entirely: a real secret never appears as literal text inside a file that gets committed to git — ever, not even once, not even temporarily. It goes into the hosting platform's environment variable settings, or into a local .env file that's explicitly excluded from git via .gitignore. Vercel, Render, and Railway all have a dedicated Environment Variables screen for exactly this — that's not a bonus feature, it's the whole reason it exists."

Vibe-Code Restock Radar → Deployed in Parallel on Render AND Railway

⏱ 24 min

A brand-new small backend app, built live in minutes — then the exact same app deployed to two different platforms side by side, so the class sees the real difference instead of taking anyone's word for it.

🎙 Instructor Says — the ask, from Tara

"Here's the request: right now, when Tara or a weekend staffer notices a title running low, the only way to flag it is texting Nikhil directly — and it gets lost in his messages within a day. Tara wants a tiny page anyone on staff can open, type a book title and a note into, and hit submit. Behind it, one small backend does two things: calls Gemini once to tag the request's urgency — Low, Medium, or High — and adds it to a running list everyone can see. That's it. That's Restock Radar."

Why this needs a real backend, not another Vercel static page

The shelf-talker page in Build 1 never talks to anything else — it's pure HTML, so a static host is perfect for it. Restock Radar is different: it has to hold a growing list of requests in memory between visits, and it has to call the Gemini API with a secret key from server-side code that never reaches the browser. Both of those need an actual server process that stays running — which is exactly what Vercel's Hobby tier is not built for, and exactly what Render and Railway both are.

🛠 Instructor Does — live, on screen

Open a vibe-coding tool the class already knows (Lovable, Bolt, or Claude Code directly in the terminal) and give it one focused prompt: "Build a small Node.js + Express app called Restock Radar. One HTML page with a form (book title, note). POST /request calls the Gemini API to tag the note's urgency as Low/Medium/High, then appends {title, note, urgency, time} to an in-memory array. GET / renders the current list, newest first. Read the Gemini key from process.env.GEMINI_API_KEY — never hardcode it." A few files will comeback. Run it once locally — npm install && node server.js (or, if the tool wired up a start script in package.json, npm start works the same) — submit one test request, confirm the urgency tag comes back and the list renders. Nothing further gets hand-written; today is about shipping it, not polishing it.

  1. Create a .env file and add it to .gitignore — before anything gets pushed. Put the real key in .env (GEMINI_API_KEY=...) and add a line .env to .gitignore. This is worth showing, not just saying: if .env is committed with the real key in it and pushed to a public GitHub repo, GitHub's own push protection throws an error and blocks the push — a live, visible consequence of skipping .gitignore, not just a rule to take on faith.
  2. Push the app to GitHub — the same Git and GitHub account confirmed ready in §2, the identical three commands from Build 1, just run inside the new folder: 
    # Terminal — run inside the restock-radar folder
git init

RENDER — WHAT THE DASHBOARD ACTUALLY ASKS FOR

A named build command and start command up front, a dedicated Environment tab for variables, and a visible free instance-hours counter. Deploy takes roughly 60–90 seconds from a clean push. First cold visit after 15 minutes idle: a real, visible wait.

RAILWAY — WHAT THE DASHBOARD ACTUALLY ASKS FOR

No build/start command needed for a standard Node app — it reads package.json itself. Variables live under a Variables tab, not "Environment." A public URL isn't automatic — it has to be switched on under Settings → Generate Domain. Deploy is comparably fast. No 15-minute spin-down on a running service — the ceiling here is the trial credit running out, not idle time.

Instructor — verify before you teach this live: re-check Render's exact "New Web Service" flow against render.com/docs and Railway's "Deploy from GitHub repo" flow against docs.railway.com the night before — both dashboards reshuffle button labels between releases.
The honest bottom line for the room: this is the whole reason Build 2 stayed small. A lightweight Node app with one in-memory list and one external API call fits comfortably inside Render's 750 free instance-hours and Railway's one-time $5 trial credit — no wall to hit today, no paid tier needed, no Docker anywhere in the picture. That's a deliberate trade: today's app can't survive a server restart (the list lives in memory, not a database) — a real product would need one, and that's a fair follow-up question to leave open, not a flaw to hide.

Free-Tier Limits — Where Each Ceiling Actually Is

⏱ 14 min

"Free" isn't a flat, permanent yes. Every platform's free tier has a specific ceiling, and it behaves differently the moment you hit it — worth knowing before it happens to a real launch, not during one.

PlatformWhat the ceiling actually isWhat happens when you hit it
Vercel Hobby100GB bandwidth/month, 100K function invocations, 4 hours of Active CPU/monthDeployments pause and functions may stop responding; existing static pages usually stay reachable.
Render Free750 instance-hours/month across free services; 15 minutes of inactivity triggers spin-downThe service sleeps. The next visitor's request cold-starts it — a 30–60 second wait before anything responds.
RailwayA one-time $5 trial credit, no renewing free allowanceThe service is paused once the credit runs out, until a card is added and a paid plan kicks in.

§ 6

Going Live For Real — Webhooks, Domains & Portfolio Value

⏱ 10 min

A live URL isn't just something to send a friend. It's the one thing that lets other automated systems find your app without a human in the loop — and it's the difference on your own CV between a claim and a link.

🎙 Instructor Says — Closing Class 18's Thread

"Remember exactly where Class 18 left off, deliberately unanswered: 'What happens the week Nikhil's on holiday, and Saturday still needs a recap sent — with nobody there to ask?' Here's the answer, and it only exists because of today. A Claude Project or a skill.md only does anything when a human opens a chat and asks. But Restock Radar now has a real, permanent public URL — which means an n8n schedule trigger or a Zapier scheduled Zap can call its list endpoint directly, every Saturday morning, and post a 'here's what's low this week' summary to the shop's WhatsApp, with nobody there to click anything. No laptop needs to be open. No human needs to remember. The summary gets generated and sent on its own, because the thing generating it finally has an address a webhook can find."

Connecting a Deployed App Back to n8n / Zapier

Once an app has a public URL, any workflow tool can treat it exactly like any other web service: an n8n HTTP Request node or a Zapier Webhooks action can call it on a schedule, pass it data, and read back the response — the same shape of connection you've already built to other APIs earlier in this course. The only new ingredient today added was the URL itself.

Portfolio value, said plainly: a screenshot of a chatbot working on someone's laptop is a claim. A link that a stranger — a recruiter, a client, an interviewer — can click and use themselves, right now, with no explanation needed, is proof. Between two otherwise-identical CV lines, the one with a live URL attached is the one that gets clicked.

Key Takeaways

1. A demo on your laptop and a shipped product are different claims. The gap between them is a public URL, not more code.

2. Vercel, Render, and Railway are not interchangeable "free hosting." Static vs. backend, spin-down vs. always-on, renewing free tier vs. one-time trial credit — pick based on the actual job.

3. A secret never appears as literal text in a committed file — ever. Environment variables exist specifically so "be careful" is never the only thing standing between you and a leak.

4. A free tier's ceiling is a specific, documented number, not a vibe. Knowing what happens at that ceiling — pause, cold-start, or exhausted credit — beats finding out live.

5. A public URL is what lets automation find your app without you. That's the whole mechanism behind a webhook triggering something on a schedule, with nobody there to click anything.

Nikhil's shelf-talker page and Restock Radar are both live now — reachable by anyone, keys held safely off to the side, and finally able to answer a schedule trigger with no one watching. But today's whole config still assumes Nikhil is the only person who ever needs to change any of it.

🎙 Instructor Says — Closing

"Leave with this one, unanswered on purpose: today, every environment variable, every Vercel project, every Render and Railway service lives under Nikhil's own account. That's fine while it's one person building everything. But what happens the day Tara or one of the weekend staff needs to update Restock Radar's key, or Sarita wants to see the Render dashboard herself, and none of them has Nikhil's login? Access, permissions, and who actually owns a deployed thing once more than one person depends on it — that's not today's problem. That's next time's."
